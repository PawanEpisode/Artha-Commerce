# F-01.2 Time Tracker rollout: exact steps

Do the parts in order. Part A is code hygiene for every change (the same as `docs/F-02-ROLLOUT.md` part A). Parts B to E are one-time. Part F is support and operations.

## A. Every code change

Follow part A of `docs/F-02-ROLLOUT.md`. Two extra points for the tracker: the API tests include a Postgres-only block (row-level security and the check constraints), so run `pytest` once against Postgres before merging; and `apps/api/modules/tracking/tests/test_web_parity.py` fails when `apps/web/src/modules/tracker/lib/limits.ts` and the API limits drift apart, so change both together.

## B. API environment (Vercel, project `arthacommerce-api`)

Nothing new to add if F-02 is live. The tracker uses the same PostHog variables:

| Name | Value |
| --- | --- |
| `POSTHOG_API_KEY` | the PostHog project key. Without it the `time_tracker` flag is not checked on the API and the tracker stays on |
| `POSTHOG_HOST` | optional, default `https://us.i.posthog.com` |

New throttle rates ship in `config/settings.py` (`tracking_write` 60 per minute, `tracking_reports` 120 per minute, `tracking_export` 6 per hour). Override them with the usual DRF settings if needed.

## C. Database migration (once per environment, from your computer)

1. `cd apps/api`, export `DJANGO_SECRET_KEY` (any value locally) and `DIRECT_DATABASE_URL`.
2. `python manage.py migrate`. It applies `tracking.0001_initial`, which creates seven tables (`tracking_studysession`, `tracking_activestopwatch`, `tracking_trackersettings`, `tracking_goal`, `tracking_dailyrollup`, `tracking_hourbucket`, `tracking_sessionaudit`), their check and unique constraints, and turns on Row Level Security for each. It depends on `syllabus.0009`. There is nothing to back-fill: F-01.1 is not built, so the table starts empty.
3. Deploy the API.

## D. PostHog

1. Create the feature flag `time_tracker`. Without it the tracker is on for everyone; set it to false to hide it. The API evaluates the same flag for the same user (needs `POSTHOG_API_KEY`), so a flag that is off also blocks the API (403 `feature_disabled`) and the web shows "not available yet". The export and delete endpoints under `/tracking/data/` are never gated, so a student can always take their data out.
2. The events are listed in the PRD section 10 and sent from the web only. Notes are never sent.

## E. Web (Vercel, project `arthacommerce-web`)

1. No new variables. Redeploy after the API is live.
2. Check as a signed-in student: `/app/tracker` shows the stopwatch and goals; start, pause, resume and stop it; open the mini timer on another `/app` page; add time by hand; edit, split, merge and delete a session and press Undo within ten seconds; set a goal; open `/app/tracker/reports` and click a heat-map day; open `/app/settings/tracker`. Switch all four themes.
3. Offline check: in the browser tools set the network to Offline, start and stop the stopwatch and add a manual entry; the page says changes are saved on the device; go back online and watch them sync (they use the same IndexedDB queue as My Coverage).
4. The reports are cached by ETag. After a write the page refetches them; the server answers 304 when nothing changed.

## F. Support and operations

- `StudySession` and `SessionAudit` are read-only in the Django admin; notes are hidden from the admin. Superusers can run **Rebuild roll-ups** on selected sessions if a student reports wrong totals. For a bulk repair run `python manage.py rebuild_tracking_rollups` (add `--user <uuid>` for one student). The roll-ups are always derived from the sessions, so a rebuild is safe.
- A student's data export and delete are in Tracker settings (`GET` and `DELETE /api/v1/tracking/data/`).
- Time forwards to coverage once, when a stopwatch stops or a manual entry is added (`study_time` events, with the session's client id). Editing, deleting, merging or splitting a session later does **not** correct the coverage ledger, because the ledger has no negative events. The Time vs coverage report reads the tracker's own totals, so it stays right.

## G. Not built yet (known)

The Pomodoro timer and its UI (F-01.1). The Pomodoro seam is in place: `register_live_timer_provider` in `services.py` (so a live Pomodoro blocks the stopwatch and the reverse) and `useLiveTimer` in the web module. Automatic capture from the study pages (`source=auto`) is reserved and not built. There is no public marketing page for the tracker yet.
